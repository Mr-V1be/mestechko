# Архитектура «Местечка»

## Слои и зависимости

```
apps/miniapp ─┐                          ┌─ packages/ui (дизайн-система, без предметной области)
apps/cabinet ─┤                          │
apps/widget ──┼─ packages/booking-ui ────┤
              │                          └─ packages/i18n (переводы, форматтеры)
              └─ @mestechko/contracts/client (типы + лёгкий клиент, без схем)

apps/api ── modules/<контекст>/{api → application → domain-порты ← infrastructure}
         └─ platform (конфигурация, БД, очереди, наблюдаемость, HTTP)

packages/contracts ── схемы Zod: источник типов API и OpenAPI
packages/domain ──── чистый домен: время, графики, календарь, доступность, вертикали, правила
```

- **Домен** (`packages/domain`) не знает о базе, сети, фреймворках и даже о Zod — это закреплено
  правилом ESLint. Здесь движок доступности, графики, политика производственного календаря,
  реестры вертикалей, статусов, ролей, каналов, источников записи и денег.
- **Приложение** (`modules/*/application`) описывает сценарии и порты. Импорт адаптеров, Nest,
  Kysely, Redis из этого слоя запрещён линтером.
- **Инфраструктура** реализует порты: Kysely-репозитории, адаптер isdayoff.ru, BullMQ, scrypt,
  подпись данных Telegram.
- **API** — контроллеры NestJS, связанные с контрактом через `@ContractRoute`.
- **Корень композиции** — `apps/api/src/app.module.ts`: модули собирают зависимости фабриками,
  доменные и прикладные классы не помечены декораторами фреймворка.

Модули API: `tenancy` (бизнесы, членство, доступ, настройки), `identity` (кабинет, сессии,
Telegram), `catalog` (каталог и его администрирование: категории, персональные условия,
несовместимые услуги), `scheduling` (графики, исключения, отсутствия, производственный
календарь), `team` (сотрудники и их графики в кабинете), `clients` (карточки, мессенджер-аккаунты
и разрешение писать), `crm` (мини-CRM кабинета: карточка, заметки, теги, импорт и экспорт),
`booking` (доступность, запись из всех каналов и с ресепшена, перенос, отмена, явка, удержание
времени, расписание кабинета), `loyalty` (леджер, баллы, абонементы, расчёт визита), `payments`
(предоплата, порт провайдера, вебхуки, возвраты), `test-pay` (эмулятор платёжного провайдера для
демо), `reports` (загрузка, выручка, неявки, повторные визиты), `notifications` (outbox сообщений
и диспетчер), `waitlist` (лист ожидания и последовательные предложения), `messaging` (каналы,
бот, доставка), `max-emulator` (эмулятор MAX Bot API для демо), `media`.
Граф зависимостей модулей ацикличен: `booking → payments, loyalty, notifications, catalog,
scheduling, clients, tenancy`; `waitlist → booking`; `messaging → booking, waitlist,
notifications`; `team, crm, reports` читают и пишут через порты своих контекстов. Реакции между
модулями (после изменения записи — доставить сообщения, предложить освободившееся время,
вернуть предоплату) связываются в корне композиции (`composition/follow-ups`) через очередь,
а не прямыми вызовами.

## Ключевые решения

**Движок доступности — чистая функция.** На вход — услуги, кандидаты с графиками и
персональными условиями, ресурсы, занятость, производственный календарь, правила, «сейчас»;
на выход — свободные старты по дням и планы бронирования. Учитывает перерывы, буферы до и после
(на краях комбинации услуг), длительности и комбинации, ресурсы разных типов, часовые пояса
и переходы на летнее время, сменные графики 2/2, исключения на даты. Время внутри — целые
миллисекунды, стены часов — Temporal (полифил, единая точка импорта). Полифил дорог, поэтому
сетка стартов дня без перевода часов строится сложением минут к полуночи, а через часовой пояс
считаются только дни с переходом (см. [performance.md](performance.md)).

**Двойная бронь невозможна в базе.** `booking_items.occupied` — `tstzrange` с ограничениями
`EXCLUDE USING gist` по сотруднику и по ресурсу для статусов, занимающих время. Статус позиции
зеркалит статус записи через составной внешний ключ с `ON UPDATE CASCADE`, поэтому их не нужно
синхронизировать в коде. Тест сверяет предикат ограничения с доменным реестром статусов.
Создание записи пробует план, а при конфликте перечитывает занятость и планирует заново
(сохранённая точка транзакции откатывает только неудачную попытку). Конфликтом считается и
взаимная блокировка: два писателя пересекающихся строк ждут друг друга внутри проверки
ограничения, и PostgreSQL прерывает одного — это та же проигранная гонка, клиент получает
`409`, а не ошибку. Нагрузочный тест подтверждает: сотня одновременных попыток на одно время
даёт ровно одну запись.

**Мультитенантность в два слоя.** Каждая таблица тенанта содержит `business_id`, ссылки между
ними — составные ключи `(business_id, id)`, так что чужой id не подставить. Плюс row-level
security: транзакция тенанта выставляет `app.business_id`, политики проверяют чтение и запись,
приложение подключается ролью без обхода RLS. Репозитории берут транзакцию из unit of work и
падают вне контекста тенанта.

**Контракты — схемы Zod.** Из них выводятся типы для сервера и клиентов, сервер валидирует
вход и сериализует ответ через схему (лишние поля не утекают), генерируются OpenAPI и лёгкий
манифест маршрутов для браузера: фронтенды не тянут Zod и libphonenumber в стартовый бандл.
Гейт проверяет, что сгенерированные артефакты актуальны. Типы таблиц Kysely генерируются из
мигрированной базы (`db:codegen --verify` в CI).

**Идемпотентность.** Создание записи требует `Idempotency-Key`; уникальность
`(business_id, client_id, idempotency_key)` в базе гарантирует одну запись на ключ даже при
параллельных запросах. Фоновые задачи схлопываются по ключу дедупликации BullMQ.

**Производственный календарь.** Порт `ProductionCalendarSource` с адаптером isdayoff.ru
(таймаут, разбор кодов праздников и сокращённых дней). Годы хранятся в PostgreSQL с ревизией,
которая растёт только при изменении данных. Синхронизация — задачи BullMQ: ежедневная по
расписанию и по требованию, если года ещё нет. Как бизнес следует календарю (закрыт в праздники,
сокращает предпраздничные дни) — политика вертикали с переопределениями бизнеса.

**Вертикали — записи реестра.** Словарь (мастер/врач/механик, кресло/кабинет/пост), типы
ресурсов, типовые услуги, правила записи (шаг сетки, горизонт, буферы, предоплата, повторные
визиты, политика календаря, стратегия выбора «любого» сотрудника). Новая вертикаль — одна
запись и переводы; тест подключает «спортшколу» без правки кода.

**Авторизация.** Mini App: каждый запрос несёт `Authorization: tma <initData>`, сервер
проверяет HMAC по схеме Telegram и свежесть по часам приложения. Кабинет: собственные сессии —
случайный токен в HttpOnly-cookie, в базе только его SHA-256, скользящий срок жизни, scrypt для
паролей, ограничение попыток входа в Redis. Права — реестр ролей с областями `schedule` и
`bookings` и охватом `own`/`all`.

**Эмулятор Telegram для демо.** Вне Telegram Mini App запускается через `mockTelegramEnv` из
SDK с данными запуска, подписанными сервером демо-ключом. Приложение вызывает только API SDK
(MainButton, BackButton, haptics), эмулятор перехватывает эти вызовы и рисует «хром» Telegram,
а нажатия возвращает в SDK событиями — один путь кода для Telegram и демо.

**Жизненный цикл записи.** Перенос, отмена и подтверждение явки — сценарии `booking`,
общие для Mini App и бота. Строка записи блокируется на время транзакции, перенос и отмена
поднимают `version`; каждое изменение пишется в `booking_events` (кто, откуда, когда, прежнее
время) — кабинет показывает эту историю. Доменные правила: статус из реестра говорит, принимает
ли запись изменения клиента, у вертикали (с переопределением бизнеса) есть срок, до которого
клиент меняет запись онлайн; действия (`confirm_attendance`, `reschedule`, `cancel`) — реестр
с условием доступности, поэтому и Mini App, и кнопки бота показывают только то, что сработает.
Перенос перепланирует те же услуги к тому же сотруднику, не считая занятым собственное время
записи, и не поднимает цену (тот же «согласованный потолок», что и при записи).

**Сообщения — outbox в той же транзакции.** Виды уведомлений — реестр домена: расписание
(по событию, за N минут до визита, по совпадению из листа ожидания), действия под сообщением,
срок, после которого сообщение устарело. Планировщик превращает событие записи в уведомление
и напоминания за 24 и 2 часа; строки пишутся в таблицу `notifications` в той же транзакции, что
и изменение, и заменяют ожидающие сообщения прежней версии записи (уникальность
`booking_id, booking_version, kind` делает планирование идемпотентным). `notifications` —
платформенная таблица: один бот служит всем бизнесам. Диспетчер (BullMQ, каждую минуту и
сразу после изменений) забирает созревшие строки `FOR UPDATE SKIP LOCKED` с арендой на 5 минут
и ставит задачи доставки; доставка собирает текст из текущего состояния записи и пропускает
устаревшее, отменённое или неразрешённое. Повторы ограничены: три аренды с ретраями BullMQ
внутри каждой, затем `failed`. Доставка — «хотя бы один раз»: падение между отправкой и
отметкой может дать повтор.

**Каналы — реестр за портом `MessengerChannel`.** Адаптер канала умеет отправить сообщение и
ответить на нажатие кнопки; сообщения описаны нейтрально (заголовок, строки, ряды кнопок),
а разметку каждый адаптер строит сам (HTML и inline-клавиатура Telegram, `inline_keyboard`
MAX). Канал без учётных данных просто отсутствует в реестре; ни одна ветка кода не сравнивает
название канала. Telegram — grammY: в разработке long polling в процессе с ролью `bot`, в
продакшене webhook `/v1/telegram/webhook` с секретом в заголовке (режим задаётся
конфигурацией); повторные обновления отсекаются по `update_id` в Redis. MAX — собственный
HTTP-клиент по публичной документации MAX Bot API (`/messages`, `/answers`, `/updates`) с
long polling и маркером в Redis. Разговор с ботом (`BotConversation`) один на все каналы:
команды `/start`, `/bookings`, `/help`, кнопки «Приду», «Перенести» (день → время →
подтверждение), «Отменить» (с последствиями), «Записаться» на предложение. Данные кнопки —
компактный код ≤ 64 байт (id в base64url, время в минутах base36); кто нажал, проверяется по
владельцу записи при каждом нажатии.

**Писать можно только тем, кто запустил бота.** `/start` записывает разрешение
(`customer_identities.messaging_allowed_at` и чат), блокировка бота его снимает. Без разрешения
сообщение пропускается с причиной `no_permission`, Mini App предлагает включить напоминания
ссылкой на бота. Кнопки Mini App в сообщениях и menu button бота включаются только при заданном
`MINIAPP_PUBLIC_URL` (https).

**Лист ожидания.** Клиент ждёт день (и часть дня) с теми же услугами и сотрудником или
«любым». Освободившееся время (отмена, перенос) ставит задачу сопоставления на день: каждому
ожидающему по очереди находится самый ранний свободный старт в его окне и цена; предложение —
уведомление с этой ценой (одно на запись листа и старт). Кто нажмёт «Записаться» первым,
тот и запишется — бронь идёт через общий сценарий записи с идемпотентным ключом и потолком
цены, запись листа закрывается в той же транзакции; остальные получают «время уже заняли».

**Эмулятор MAX.** Реального бота MAX нет, поэтому в демо API отдаёт подмножество MAX Bot API
под `/max-emulator` (включается `MAX_EMULATOR_ENABLED` только в демо-режиме) и хранит диалоги
в своих таблицах — как это делали бы серверы MAX. Бот работает с ним через тот же адаптер,
что и с настоящим MAX; смена адреса и токена переводит канал на реальный сервис. Экран кабинета
«Эмулятор MAX» показывает чаты клиентов бизнеса и позволяет нажимать кнопки и писать боту за
клиента.

**Ресепшен в кабинете.** Запись, перенос (перетаскиванием и формой), отмена, «визит
состоялся» и «не пришёл» — сценарии `booking` с теми же проверками движка доступности и
ограничениями базы, что у клиентских каналов; бизнес не связан сроком онлайн-изменений.
Каждое изменение называет версию записи, которую видел человек: если запись успели изменить,
ответ — `409` с причиной, а не тихая перезапись. Кабинет переносит блок сразу (оптимистично),
при отказе возвращает его на место и объясняет причину там, где его бросили; тост переноса
даёт «Вернуть». Клиент узнаёт об изменении через ту же очередь уведомлений, в свой мессенджер:
уведомление о переносе с ресепшена ждёт минуту, а неотправленные уведомления помнят, что клиент
знал до изменения, — если запись вернули туда же, клиенту не приходит ничего.
Действия — реестр домена с условием доступности, поэтому кабинет показывает только то, что
сработает, а у опасного действия — последствия (уведомление клиенту, возврат предоплаты).

**Удержание времени.** Статус `held` занимает время, но запись ещё не подтверждена. Причины —
реестр (`payment`, `waitlist_offer`) со сроком из правил. Подтверждение снимает удержание,
истёкшие удержания освобождает ежеминутная задача, отказ от оплаты освобождает время сразу.
Освободившееся время уходит листу ожидания.

**Предоплата.** Порт `PaymentProvider` (создать оплату, вернуть, разобрать вебхук), реализация
выбирается конфигурацией. Доля — правило вертикали или бизнеса и, при необходимости, своя у
услуги; сумма считается доменом в целых копейках. Вебхуки проверяются подписью, каждое событие
записывается один раз (`payment_webhook_events`), поэтому повтор ничего не меняет. Возврат —
по правилу домена: всегда при отмене заведением, при отмене клиентом — пока изменения открыты;
поздняя отмена и неявка оставляют предоплату. Возвраты идут задачей после фиксации транзакции
и добираются периодической проверкой. «Тестовая касса» — эмулятор провайдера со своими
таблицами, API и страницей оплаты, как у настоящего провайдера.
Где открывается страница оплаты — возможность провайдера в реестре (`checkoutPresentations`):
встроенная (как «Тестовая касса») открывается вместо приложения и возвращает в него, внешняя —
в браузере (`WebApp.openLink` в Mini App, новое окно из виджета); плательщик попадает на
нейтральную страницу «Оплата завершена», а приложение само замечает оплату и подтверждает
запись. `TEST_PAY_CHECKOUT=external` показывает этот путь на тестовой кассе.

**Деньги и баллы — леджер.** Все движения (предоплата, возврат, оплата визита, начисление и
списание баллов, продажа и визит по абонементу) — строки в целых единицах с причиной из реестра;
таблица только дописывается (триггер запрещает правку и удаление). Баланс — сумма проводок.
Программа лояльности — данные бизнеса по реестру видов; расчёт визита (`settleVisit`) — функция
домена, её же вызывает кабинет, чтобы до закрытия показать «к оплате» и «начислим».

**Графики сотрудников.** Шаблоны (5/2, 2/2, 3/3, по дням недели, свой цикл) — реестр домена,
плюс исключения на даты и отсутствия (отпуск, больничный). Перед сохранением API показывает,
какие записи окажутся вне рабочего времени («Затронет 3 записи»); подтверждение повторяет
расчёт и, если записи успели измениться, просит посмотреть ещё раз.

**Каталог.** Категории, персональные цены и длительности сотрудников, своя доля предоплаты у
услуги и несовместимые пары услуг. Несовместимость проверяет домен при любой записи; клиентские
приложения сразу гасят услугу, которую нельзя добавить, и говорят почему.

**Мини-CRM.** Карточка клиента собирает историю визитов, неявки, заметки, теги, баллы и
абонементы. Импорт и экспорт CSV и Excel идут через файловые контракты: импорт сначала
проверяет файл и показывает, что добавится, обновится и будет пропущено (с причиной по строке).

**Отчёты.** Метрики — реестр домена над фактами периода (рабочее и занятое время, выручка,
визиты, неявки, повторные клиенты); SQL собирает факты по дням в часовом поясе филиала.
У каждого графика есть табличное представление, цвета и оси — токены обеих тем.

**Лист ожидания — по очереди.** Освободившееся время предлагается первому подходящему
ожидающему и удерживается за ним N минут (N — правило вертикали с переопределением бизнеса);
отказ или истечение передают предложение следующему. Ответить можно кнопками бота или в Mini App
(запись «Ожидает» с кнопками «Записаться» и «Не подходит»); принятие подтверждает удержанную
запись, а если нужна предоплата — переводит удержание на оплату.

**Виджет для сайта.** Скрипт `widget.js` (классический, без зависимостей) читает атрибуты
своего тега и рисует форму в iframe — стили сайта и формы не пересекаются; его собственные
кнопка и окно живут в Shadow DOM с токенами дизайн-системы. Высота встроенной формы следует за
содержимым через `postMessage` (только размеры и факт записи, без персональных данных).
Запись с сайта не требует аккаунта: API отвечает токеном (HMAC), который подтверждает, что
посетитель сделал эту запись, и ограничивает частоту по адресу. Страница оплаты возвращает
посетителя в форму по идентификатору попытки, вкладка помнит, какой записью она стала.

**Наблюдаемость.** Структурные логи pino с id запроса, пользователем, тенантом и trace id;
метрики OpenTelemetry (HTTP, бизнес-счётчики) на `/metrics` для Prometheus; трассы HTTP и
PostgreSQL выгружаются по OTLP, если задан коллектор. Готовность — `/health/ready`.

## Языки

**Порядок выбора языка — одна функция домена** (`resolveLocale`): сохранённый выбор
человека, затем языки, о которых сообщает платформа (Telegram `language_code`, MAX
`user_locale`, языки браузера по предпочтению), затем английский. Реестр языков
(`packages/domain/src/locales`) говорит, какие мессенджеры предлагают читателям языка
(MAX — только русскоязычным) и в какой валюте продаются тарифы для этой аудитории. Новый язык —
запись в реестре и переводы; гейт `pnpm gate:locales` проверяет, что у каждого языка есть все
ключи, плейсхолдеры и нужные его грамматике формы множественного числа.

**Переводы грузятся по языку.** Приложение загружает только показываемый язык (общие и свои
пространства имён), другой — при переключении. Веб-приложения хранят выбор в `mst-locale`:
на одном адресе сайт продукта, кабинет и виджет говорят на выбранном в любом из них. Mini App
хранит выбор на сервере (`customers.locale`), поэтому бот пишет на нём же; язык Telegram
запоминается в `customer_identities.language_tag` с каждым обновлением и нужен для
напоминаний, которые уходят позже. Сервер отвечает на языке из `Accept-Language`, который
приложения выставляют по выбору читателя; страница оплаты получает язык плательщика при
создании платежа, как у настоящих провайдеров, нейтральная страница возврата — в адресе.

**Сайт продукта — страница на язык.** Русская — на корне, английская — `/en/`, обе
отрендерены заранее со своими `<title>`, описанием и `hreflang`. Скрипт в `<head>` до первой
отрисовки открывает страницу языка посетителя.

**Деньги, даты, телефоны.** Суммы — в валюте заведения через один форматтер; время — как
пишут в языке читателя (`09:05`, `9:05 AM`), промежутки — одной записью (`10:00 – 11:30 AM`),
в часовом поясе филиала. Подсказки и примеры телефонов, демо-диапазоны — по стране заведения.

## Выбор технологий

- **Кабинет на Vite, а не Next.js.** Кабинет — приложение за авторизацией без SEO; данные
  приходят из отдельного API; серверный рендеринг не даёт выгоды, а добавил бы второй серверный
  рантайм. Vite даёт статическую сборку, общий с Mini App инструментарий и дизайн-систему.
- **TypeScript 6.0.** TypeScript 7 (нативный) уже вышел, но typescript-eslint поддерживает
  только < 6.1: типизированный линт важнее.
- **SDK Telegram — `@tma.js/*`.** Это официальный SDK проекта Telegram Mini Apps; пакеты
  `@telegram-apps/*` переименованы и помечены авторами как неподдерживаемые.
- **Kysely + SQL-миграции.** Ограничения уровня PostgreSQL (exclusion, RLS, составные ключи)
  выражаются напрямую, типы генерируются из схемы.
- **Base UI** — доступные примитивы (select, dialog, toast, radio) для дизайн-системы.
- **OpenTelemetry для метрик** вместо prom-client: последний заменён авторами.

## Процессы

Один образ API, роли процесса задаются `APP_ROLES`: `api` (HTTP), `worker` (очереди BullMQ:
доставка и напоминания, лист ожидания, удержания, возвраты, календари), `bot` (обновления
ботов: long polling в разработке, в продакшене — регистрация вебхука Telegram и чтение MAX;
ровно один такой процесс на бота). В разработке один процесс выполняет все три роли. Тот же
образ выполняет миграции и ночной сброс демо (`demo:schedule`, планировщик BullMQ с
часовым поясом). Процессы без HTTP обновляют файл-пульс, пока отвечают база и Redis, —
по нему их проверяет Docker. Продакшен-стек и выкатка — в [deploy.md](deploy.md).

## Гейты

`pnpm gate`: файл ≤ 700 строк и папка ≤ 15 файлов исходников, только токены дизайн-системы
в стилях и разметке, одинаковые ключи переводов во всех языках, Prettier, ESLint (strict type-checked + границы слоёв), typecheck всех
пакетов, актуальность OpenAPI и манифеста, unit-тесты. CI дополнительно гоняет интеграционные
тесты на PostgreSQL и Redis, сверку типов БД со схемой и полный seed.
