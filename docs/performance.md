# Нагрузочное тестирование

Путь клиента под нагрузкой: подбор свободного времени, бронирование одного и того же окна
множеством клиентов одновременно и «Мои записи». Сценарий — `tooling/load/booking-load.js`,
инструмент — k6 из официального Docker-образа `grafana/k6`, без установки в систему.

## Стенд

- **Сборка** — продакшен-стек `docker-compose.prod.yml`, поднятый локально целиком: Caddy
  с TLS, образы api/worker/bot, PostgreSQL 18, Redis 8. Запросы идут так же, как от
  Mini App: через Caddy, по HTTPS, с префиксом `/api`.
- **Ограничения ресурсов** — как у скромного VPS: `api` — 1 vCPU, `postgres` — 1 vCPU,
  `edge` (Caddy) — 0,5 vCPU, `redis` — 0,25 vCPU (`docker update --cpus`).
- **Машина** — AMD Ryzen 9 8945HX, 32 ГБ ОЗУ. Параллельно работали другие проекты,
  поэтому на пределе пропускной способности результаты заметно «гуляют».
- **Данные** — демо из сида: четыре заведения, около 3 100 записей (тогда — восемь недель
  истории; сейчас сид даёт четыре месяца, около 7 400 записей). Перед каждым прогоном демо
  пересоздаётся.

## Сценарии

| Сценарий      | Что делает                                                                                                                        | Нагрузка                                           |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `slots`       | `GET /availability`: свободное время на случайную неделю ближайших двух недель, «любой мастер»                                    | постоянный поток RATE запросов/с, 60 с             |
| `contention`  | `POST /miniapp/.../bookings`: CONTENDERS клиентов одновременно бронируют один и тот же старт у одного мастера; так 10 окон подряд | CONTENDERS виртуальных пользователей × 10 итераций |
| `my_bookings` | `GET /miniapp/.../bookings?scope=upcoming` от случайного клиента прогона                                                          | постоянный поток RATE запросов/с, 60 с             |

Каждый клиент — отдельный демо-пользователь Telegram с подписанными данными запуска
(`POST /v1/demo/telegram-launch`), как в эмуляторе Mini App. Окна выбираются в `setup()`:
у одного мастера, по одному на день (окна не пересекаются), услуга без предоплаты.

Пороги (thresholds) прогона: p95 подбора слотов < 500 мс, p95 «Моих записей» < 300 мс,
ошибок < 1 %, **ровно одна запись на каждое окно** (`bookings_created == 10`) и **ни одного
ответа, кроме 201 и 409** (`bookings_unexpected == 0`).

После прогона база проверяется запросом `tooling/load/double-bookings.sql`: пары записей,
занимающих одного мастера или ресурс в пересекающееся время. Ответ должен быть пустым.

## Результаты

| Поток (RATE) | Претендентов на окно | Подбор слотов: p50 / p95 / p99 | «Мои записи»: p50 / p95 | Бронирование: p50 / p95 | Ошибки | Записей / отказов 409 | Двойные брони |
| -----------: | -------------------: | ------------------------------ | ----------------------- | ----------------------- | -----: | --------------------- | ------------: |
|       50 rps |                   40 | 13,9 / 117 / 307 мс            | 3,8 / 7,2 мс            | 373 / 514 мс            |    0 % | 10 / 390              |             0 |
|      100 rps |                  100 | 13,4 / 45 / 144 мс             | 3,1 / 5,1 мс            | 695 мс / 1,41 с         |    0 % | 10 / 990              |             0 |
|      150 rps |                  100 | 0,96 / 2,46 / 3,3 с            | 3,4 / 14 мс             | 791 / 923 мс            |    0 % | 10 / 990              |             0 |

- **Подбор слотов** держит 100 запросов/с на одном vCPU API с p95 45 мс. На 150 запросах/с
  API упирается в процессор: k6 недосчитался 519 итераций, p95 растёт до секунд, но ошибок
  нет. Предел одного vCPU — около 120–140 запросов/с; API не хранит состояния, и
  следующий шаг — вторая реплика `api` за тем же Caddy.
- **Бронирование под конкуренцией**: 100 клиентов, нажимающих «Записаться» на одно и то же
  время, получают ровно одну запись и 99 ответов `409 slot_unavailable`. На 10 окнах — 10
  записей и 990 отказов, повторов и ошибок нет. Время ответа здесь — это сотня
  одновременных транзакций на одном vCPU: каждая пересчитывает свободное время и
  пробует вставку.
- **«Мои записи»** — лёгкое чтение: p95 в единицах миллисекунд на всех уровнях.
- **Двойных броней нет** ни в одном прогоне: проверка по базе возвращает ноль пар.
  Гарантия на стороне базы — exclusion-ограничения на `booking_items.occupied` по мастеру
  и по ресурсу; приложение лишь выбирает, кому из мастеров отдать время.

## Что нашёл тест и что исправлено

1. **Подбор слотов упирался в часовые пояса.** Первый прогон на 50 запросах/с: p95
   6,98 с, среднее 4,6 с, 305 итераций k6 не успел запустить. Профиль процессора
   (`node --cpu-prof`) показал, что больше половины работы — Temporal-полифил: сетка стартов
   дня (10:00, 10:15, …) строилась переводом каждой отметки через часовой пояс туда и
   обратно, 96 преобразований на день. Теперь дни без перевода часов (почти все)
   считаются сложением минут к полуночи, а точный путь остался для дней с переходом на
   летнее или зимнее время. Тесты сравнивают обе сетки, в том числе на днях перевода часов
   в Берлине и на получасовом поясе. Итог: p95 на 50 запросах/с — 117 мс вместо 6,98 с.
2. **Под конкуренцией около 1 % бронирований заканчивались ошибкой 500**
   (`deadlock detected`, 11 из 1000 на сотне претендентов). Две транзакции вставляют
   пересекающиеся строки, каждая внутри проверки exclusion-ограничения ждёт
   незафиксированную строку другой, и PostgreSQL прерывает одну из них, чтобы разорвать
   взаимную блокировку. По смыслу это та же проигранная гонка за время, что и нарушение
   ограничения: теперь обе ошибки откатывают только точку сохранения попытки, и
   бронирование пробует следующего мастера или честно отвечает `409`. Интеграционный тест
   отправляет 24 одновременных запроса на одно время и ждёт ровно один `201` и 23 `409`.

## Как запустить

Нужен поднятый продакшен-стек (локально: [docs/deploy.md](deploy.md), «Пробный запуск на
своей машине») с демо-данными.

```sh
# Ограничения ресурсов, как в таблице выше (необязательно)
docker update --cpus 1 mestechko-prod-api-1 mestechko-prod-postgres-1
docker update --cpus 0.5 mestechko-prod-edge-1
docker update --cpus 0.25 mestechko-prod-redis-1

# Чистые демо-данные
docker compose --env-file .env.production -f docker-compose.prod.yml --profile demo \
  run --rm --no-deps demo-reset node dist/cli/seed.js

# Прогон: RATE — поток чтений в секунду, CONTENDERS — претендентов на окно
docker run --rm --network host -v "$PWD/tooling/load:/scripts:ro" \
  -e RATE=100 -e CONTENDERS=100 grafana/k6:1.3.0 run /scripts/booking-load.js

# Двойные брони: ответ должен быть пустым
docker compose --env-file .env.production -f docker-compose.prod.yml exec -T postgres \
  psql -U mestechko -d mestechko < tooling/load/double-bookings.sql
```

Другие параметры сценария: `BASE_URL` (по умолчанию
`https://miniapp.mestechko.localhost:46291/api`), `BUSINESS` (`siren`), `DURATION` (`60s`),
`WINDOWS` (`10`). Для адресов `*.localhost` k6 сам направляет запросы на 127.0.0.1 и
принимает сертификат локального центра Caddy.
